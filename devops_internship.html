Learning DevOps by building it on AWS

A remote, mentor-led internship where I was assigned to a DevOps team and worked through real tasks, from a first EC2 server to serverless apps with CI/CD, documenting every one in a report.

organisationConfidencEway
formatRemote, mentor-led
scope24 task reports · 60 internship days
focusAWS · Docker · CI/CD

the internshipHands-on learning, one task at a time

I was placed with a DevOps team that sent me tasks, each building on the last. I worked on my own AWS environment, and for every task I wrote a report with screenshots of what I built, an explanation of the concepts in my own words, the problems I ran into, and questions for my mentor.

The reports were part of the work. Explaining why something works, and what went wrong on the way, taught me as much as getting it running.

By the end I had moved from launching a single server to running load-balanced containers, automated pipelines and serverless services, and had a habit of securing and monitoring each of them as I went.

the pathSix stages across 60 days

Days 1 – 5

Cloud, Linux and the first server

Started with cloud and Linux fundamentals, then explored the core AWS services (VPC, EC2, IAM, S3, Lambda, CloudWatch). Launched my first EC2 instance, locked SSH to my own IP, and served pages with Nginx, including a reverse proxy and simulated load balancing.

AWS EC2IAMSecurity groupsSSHNginx
Days 6 – 10

From a small app to containers

Built a Node.js and Express backend, ran several instances behind Nginx with weighted load balancing, and added health checks that routed around a killed instance. Then packaged the app in Docker and ran Nginx plus multiple app containers from one Docker Compose file.

Node.jsExpressDockerDocker ComposeNginx upstream
Days 12 – 21

Hardening, automation and monitoring

Created individual SSH-key users, disabled root login and locked the default account. Wrote a bash script scheduled with cron and log rotation, then installed the CloudWatch agent to track memory and disk usage and raise an email alarm. Also wrote a client-facing one-pager on WhatsApp Official Business Accounts.

Linux usersSSH keyssudoersBashcronCloudWatch agentSNS alarms
Days 25 – 32

Git and my first pipeline

Learned Git and GitHub properly: commits, branches, pull requests and merging. Built a GitHub Actions workflow that tests the app on every push, then added a deploy job that ships to EC2 using GitHub Secrets. Compared Bitwarden and LastPass for a team in a written report.

GitGitHubGitHub ActionsCI/CDSecrets
Days 42 – 45

Load balancing, image hardening and serverless

Ran the app on two EC2 instances behind an Application Load Balancer, then stopped one container to watch it fail over and recover. Researched protecting source code in a Docker image and built a signed, instance-bound licence check. Created my first Lambda functions behind API Gateway.

ALBTarget groupsMulti-stage buildsLambdaAPI Gateway
Days 50 – 60

Observability, serverless apps and cost

Built a CloudWatch Synthetics canary with an alarm, then a serverless URL shortener on Lambda, API Gateway and DynamoDB. Rebuilt it with an OIDC-based GitHub Actions pipeline that can update one Lambda function and nothing else. In the final task I reviewed an AWS account’s billing and wrote a cost-optimization plan.

CloudWatch SyntheticsDynamoDBOIDCLeast privilegeCost Explorer

highlightsThree things I’m proud of

Load-balanced containers

The same Dockerised Express and Nginx app ran on two EC2 instances behind an Application Load Balancer. When I stopped one container, the balancer marked it unhealthy, sent all traffic to the other, and resumed sharing once it recovered.

Least-privilege deployments

A GitHub Actions pipeline deploys a Lambda function using short-lived credentials from OIDC, with a role allowed to do exactly one thing. When it first failed, I traced it to the repository subject format in the trust policy and fixed it.

OIDCIAMGitHub Actions

Serverless URL shortener

A POST route creates a short code stored in DynamoDB, and a GET route looks it up and redirects. I built it twice, the second time with a proper repository and an automated deployment.

takeawaysWhat I took away

Troubleshooting is the job

A full disk, a port already in use, a typo in a Compose file, a trust policy in the wrong format. Reading the error and narrowing it down was a bigger skill than knowing the commands.

Least privilege everywhere

Individual users instead of shared logins, SSH keys, scoped IAM roles and short-lived credentials. Security came up in almost every task.

Know what can’t be done

While researching how to protect source code in a Docker image, I found that a privileged host admin can always export it. The honest answer was to harden it, gate it with licences and say so clearly.

Write it down, ask questions

Explaining each task in a report and ending with open questions turned every task into a conversation with my mentor, and made me understand it properly.
